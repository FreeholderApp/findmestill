# FindMeStill transport pilot

Discovery v0.1 defines a portable contact ID and signed card chain. The next interoperability milestone pairs discovery with a maintained encrypted transport. Select a delivery profile after executing the same cases against SimpleX and Nostr/Marmot.

## Shared scenario

Use synthetic Studio, Customer and Assistant identities, a second Customer device, the same attachment bytes and the same measured offline interval. Start with empty client state and independently controlled hosts. Pin the Studio card before any move. Record the client, server and library versions and the initial browser or phone workflow.

| Case | Required evidence |
| --- | --- |
| Establish contact | Starting at the same Studio share link, record the time, steps and any client install. Identify which app holds the reply identity. |
| Deliver offline | Shut down the receiving client, send the fixture and record immediate acknowledgement, the storage operator and retention guarantee. Reconnect and verify one decrypted copy. |
| Retry | Repeat the same FindMeStill message identifier after a lost response. Read the storage result and recipient history. A transport upload or relay event acknowledgement alone cannot establish the proposed receipt semantics. |
| Return and reply | Close the customer browser or app, reopen on the original authorized endpoint and then on a second authorized device. Verify the reply and report every setup or recovery step. |
| Revoke collaborators | Remove the Assistant and send new content. Check that the remaining devices can read it and the removed endpoint cannot. Remove the second device in a separate run and repeat. |
| Recover after moving | Stop the original HTTPS site, publish a signed successor at the saved backup and reconnect. Verify the same contact ID and thread. Record whether credential replacement preserves history, delivery routing, or both. |
| Retrieve a file | Encrypt the same fixture using a maintained implementation. Compare ciphertext integrity and retrieval across HTTPS and an optional second IPFS provider, with equivalent retention. Record bytes and time to first playable content. |
| Continue the relationship | Stage authenticated voice/video and an encrypted scheduling message bound to the saved identity. Record support, explicit permissions and gaps separately. |

For SimpleX, use its maintained chat client and the SMP and XFTP servers. Record which functions require a native client or a service bridge. For Nostr/Marmot, use a maintained MLS client and independent relay. Record its event acknowledgement and whether a removed leaf can decrypt a post-removal application message. Exercise ordinary NIP-17 in a separate test. A NIP-17 pass supplies no evidence about MLS membership.

Record each result as verified, failed, or pending, with exact commands and client-visible observations. A compatibility pass requires both independent systems to complete the same user-visible case. Delivery, root continuity, private history and storage guarantees require distinct evidence.
